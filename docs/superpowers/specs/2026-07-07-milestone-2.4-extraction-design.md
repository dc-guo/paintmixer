# Milestone 2.4 — Extraction Upgrades (Design)

- **Date:** 2026-07-07
- **Phase:** 2 (Richer Color Tools) — see `temp/plans/PHASE_2_COLOR_TOOLS.md` §2.4
- **Status:** Approved design, pre-implementation
- **Branch:** `working` (accumulates with the phase; no per-milestone PR)

## Goal

Give the user control over how many colors are pulled from their artwork, and
make the colors that get pulled better — fewer near-duplicate neutrals, better
odds that a small-but-salient color earns a slot. Two shipping parts:

1. **Palette-size control** — a 3–8 stepper (default 5), persisted.
2. **Better clustering** — replace frequency-bins + greedy separation with
   deterministic k-means in Lab space, seeded from the current top-bin picks.

### Non-goals

- **Region re-extraction** (the plan's stretch item) — parked unless requested.
- Measured pigment data, ICC, or any AI/randomized clustering. Color math stays
  deterministic (guardrail 4).
- No change to the append/merge behavior of "Re-generate" (see Interaction).

## Interaction model (decided)

- The size stepper sets a **persisted preference only**. Changing it does not
  trigger extraction. The value is applied on the next **Re-generate** or when
  **new artwork** is selected.
- **Re-generate keeps today's append/merge semantics:** it adds newly-found
  distinct colors on top of the working palette and preserves colors the user
  added manually or moved. `N` is the extraction target count, not a cap on the
  working palette's total size.
- New artwork continues to start a fresh working palette of up to `N` colors.

## Detailed design

### 1. Palette-size control + persistence

```
// storage.ts
PALETTE_SIZE_KEY = 'paintbridge.paletteSize.v1'
MIN_PALETTE_SIZE = 3
MAX_PALETTE_SIZE = 8
DEFAULT_PALETTE_SIZE = 5

clampPaletteSize(n)   -> round then clamp to [MIN, MAX]
loadPaletteSize()     -> finite number in range, else DEFAULT
persistPaletteSize(n) -> clampPaletteSize then best-effort try/catch write
```

- Brand-new key ⇒ backward compatible by construction (absent → default 5; no
  migration). Consistent with the existing best-effort persistence pattern
  (private mode / quota failures are swallowed).
- UI: the stepper mirrors the existing `MixEditor` −/+ affordance for
  consistency; − disabled at 3, + disabled at 8; keyboard accessible; shows the
  current `N`. Lives in the `.strip-caption` row beside "Re-generate".

### 2. k-means clustering (deterministic), inside `extractPaletteFromPixels`

1. **Bin** (unchanged): 4-bit/channel buckets (≤4096 bins); skip alpha < 128;
   each bin tracks `count`, sum r/g/b, `firstIndex`, `sumX`, `sumY`.
2. **Precompute per bin:** mean RGB (`round(sum/count)`) and
   `lab = rgbToLab(meanRgb)`, cached on the bin. Caching Lab per bin is why we
   cluster ~4096 bins instead of ~25k pixels — same result, far less work.
3. **Seed** (reuse today's greedy separation; deterministic): rank bins by
   `count` desc, greedy-pick up to `K = maxColors` using progressively relaxed
   thresholds — now measured with `labDistance`. `SEPARATION_THRESHOLDS` retunes
   to Lab units, starting `[24, 16, 8, 1]` (tunable; validated in UAT; the final
   `1` still blocks near-exact-duplicate seeds). This spread-out pick is a
   deterministic stand-in for k-means++ initialization. Fewer distinct bins than
   `K` ⇒ `K` shrinks to what exists.
4. **Iterate** (fixed cap 10; early-exit when assignments stop changing):
   - **Assign:** each bin → index of nearest centroid by `labDistance`; ties
     resolve to the lowest centroid index (deterministic).
   - **Update:** each centroid = count-weighted mean Lab of its assigned bins;
     clusters that end a round with no bins are dropped.
   - **Stop** when no bin changes cluster, or the cap is reached.
5. **Emit**, clusters ordered by total `count` desc:
   - **color** = count-weighted **mean RGB** of member bins → `rgbToHex`
     (avoids needing a Lab→RGB inverse).
   - **position** = per §3.
   - Output length ≤ `maxColors`.

**Determinism guarantee:** bin `Map` scan order is fixed by pixel order; the
greedy seed is deterministic; assignment ties break by index; the iteration cap
is fixed; no `Math.random` / `Date`. Same pixels + same `N` ⇒ byte-identical
output.

### 3. Position / marker output

Each cluster spans several bins. Aggregate over member bins:
`sumX`, `sumY`, `count` → candidate centroid pixel `(cx, cy)`
(`round(sumX/count)` / `round(sumY/count)`, clamped to `width-1` / `rows-1`).

Build a `binKey → clusterIndex` map (O(1) lookups). Apply today's fallback: if
the pixel at `(cx, cy)` maps to *this* cluster, use the centroid; otherwise fall
back to the `firstIndex` of the cluster's highest-`count` member bin (a pixel
guaranteed to be in-cluster). Emit `x = (px + 0.5) / width`,
`y = (py + 0.5) / rows`.

This preserves the current marker/drag/arrow-key behavior — markers keep landing
inside their color's region, even when a cluster is spatially split.

## Data flow

```
user sets N (stepper)
  └─ changePaletteSize → persistPaletteSize(N) + setPaletteSize(N)   [App]
next Re-generate / new artwork
  └─ extractPaletteFromDataUrl(dataUrl, N)
        └─ extractPaletteFromPixels(pixels, width, N)   [k-means]
              └─ ExtractedColor[] (≤ N)  →  merged (append/dedup) into workingColors
```

## Testing plan

**Pass unchanged** (hand-verified against the new pipeline — one bin per color
reduces k-means to the same picks/positions):
- dominant-first ranking; ignores mostly-transparent; never-returns-duplicates;
  respects requested count; representative-location (2×2); band-center (4×4).

**Changed assertion:**
- *"prefers visually distinct over near-duplicates"* — k-means now **merges** two
  near-duplicate reds into one averaged-red cluster (the intended improvement).
  Relax `palette[0] === '#FF0000'` to "red-dominant (r ≫ g, b)"; palette[1]
  stays blue. (The plan anticipates "band/position tests updated for k-means.")

**New tests:**
- **Determinism:** same pixel array + same `N` → `deepEqual` across two calls.
- **Merging:** two near-duplicate clusters + one distinct color, `N = 2` →
  returns 2 colors; the merged representative sits between the two inputs.
- **Storage size helper:** clamps out-of-range, defaults on garbage, round-trips.

**Manual (UAT):** on 2–3 real photos, confirm the k-means palette visibly beats
the current one — fewer near-duplicate neutrals, better coverage of small salient
colors — and that the stepper choice persists across reload.

## Edge cases / error handling / performance

- **Empty/collided seed clusters** are dropped ⇒ output may be < `N` (matches the
  current "return only what exists" behavior; the dedup test still holds).
- **Fewer distinct bins than `N`** ⇒ `K` shrinks at seed time.
- **All-transparent image** ⇒ no bins ⇒ `[]`. `extractPaletteFromDataUrl`
  null-context / image-load failure ⇒ `[]`; callers already `try/catch`.
  Unchanged.
- **Performance:** ≤4096 bins × `K ≤ 8` × ≤10 iters ≈ 3.3e5 `labDistance` ops
  worst case, plus ≤4096 Lab conversions — comfortably under the ~50ms
  mix-search budget. Spot-check timing during verification; not a risk.
- **Persistence** is best-effort (private mode / quota) like the existing keys.

## Acceptance criteria

- **Determinism:** same image + same settings always yields the same palette
  (covered by the determinism test).
- **Markers:** position/marker tests pass; markers land inside their color's
  region.
- **Quality:** manual check on 2–3 photos shows fewer near-duplicate neutrals and
  better coverage of small salient colors than the current extractor.
- **Size control:** stepper offers 3–8 (default 5), persists across reload, and
  is applied on Re-generate / new artwork; append/merge semantics unchanged.
- **Compatibility:** old saved palettes and existing owned-paint ids are
  untouched; `npm test` (tsc + node --test) green.
